# Decision — 초등 음악 작곡 도구 기본 아키텍처

## 상태

초기 방향 결정.

## 목표

초등학생이 전문 기보 프로그램의 복잡성 없이 음악을 만들고, 동시에 자신이 만든 결과가 실제 음악 개념과 오선보로 어떻게 연결되는지 이해할 수 있게 한다.

## 핵심 결정

### 1. 입력과 오선보를 분리한다

학생의 주 입력은 오선보가 아니라 직관적인 grid를 사용한다.

그러나 최종 결과는 실제 오선보로 변환한다.

```text
Grid Input
   ↓
Canonical Song Model
   ├─ Audio Playback
   ├─ Theory Feedback
   └─ Staff Notation
```

오선보와 그리드는 별도 데이터가 아니라 동일한 곡 상태를 바라보는 두 view다.

---

### 2. Guided와 Free 모드를 분리한다

초기 학습:

> 도움받아 만들기

심화:

> 자유롭게 만들기

guided 모드에서는:

- 음계
- 음역
- 마디 수
- 박자
- 화음 후보
- 리듬 복잡도

를 제한한다.

free 모드에서는 제한을 점차 해제한다.

---

### 3. 음악 데이터는 문자열이 아니라 구조화된 pitch/time으로 저장한다

화면에 “도”, “레”, “미”라고 표시해도 내부 핵심 값은 MIDI 또는 동등한 pitch representation을 사용한다.

```ts
type NoteEvent = {
  pitch: number
  onsetBeats: number
  durationBeats: number
}
```

이 구조는:

- 재생
- 오선보
- 조표
- 임시표
- 화음 분석
- MIDI
- 전조

에 공통으로 사용할 수 있다.

---

### 4. 기본 작곡 단위는 4마디로 시작한다

처음에는:

- 4/4박자
- 4마디
- 1옥타브 전후
- 단순 리듬
- I·IV·V 계열 화음

을 사용한다.

음악적 구조:

```text
1마디: 제시
2마디: 반복/작은 변화
3마디: 대조/발전
4마디: 종지
```

를 기본 guided template으로 사용한다.

---

### 5. 변형 명령을 1급 기능으로 둔다

초등 작곡에서는 빈 화면보다 기존 아이디어를 변형하는 기능이 중요하다.

초기 명령:

- 마디 복사
- 한 음 바꾸기
- 끝음 바꾸기
- 위/아래 반전
- 리듬 일부 바꾸기
- 음역 올리기/내리기

각 명령은 undo 가능해야 한다.

---

### 6. 오답 판정기가 아니라 청음 비교 도구로 만든다

음악 창작에서 화음 밖 음을 모두 오류로 처리하지 않는다.

피드백:

- 안정적으로 어울리는 음
- 자연스럽게 지나가는 음
- 긴장감 있는 음
- 다시 들어볼 음

등으로 구분한다.

가능하면:

```text
[현재 그대로 듣기]
[추천 바꾼 버전 듣기]
```

를 제공한다.

---

### 7. 리듬 기능은 단계적으로 연다

Phase A:

- 4분음표 중심
- 한 박 한 음 또는 쉼

Phase B:

- 2분음표
- 8분음표
- 쉼표

Phase C:

- 점음표
- 붙임줄
- 당김음

한 화면에서 처음부터 모든 음표를 제공하지 않는다.

---

### 8. 계이름과 음이름을 분리해 보여 준다

예:

```text
계이름: 도
음이름: G
```

조성에 따라 계이름의 역할과 실제 pitch가 달라지는 점을 UI가 명확히 표현해야 한다.

---

### 9. 교사용 기능은 학생 작곡 화면과 분리한다

학생:

- 만들기
- 듣기
- 고치기
- 저장
- 제출

교사:

- 과제 생성
- 접속 링크/QR
- 제출물 모아보기
- 학생별 버전
- 발표작 선택/전시
- 피드백

교사용 관리 기능이 학생 창작 화면을 복잡하게 만들지 않게 한다.

---

### 10. 저장 계층을 분리 가능하게 설계한다

```ts
interface SongRepository {
  save(song: Song): Promise<void>
  load(id: string): Promise<Song | null>
  list(): Promise<Song[]>
}
```

초기에는 LocalSongRepository.

후속에는 CloudSongRepository.

UI가 저장 방식에 직접 의존하지 않도록 한다.

## 첫 프로토타입에서 검증할 것

1. 학생이 설명 없이도 음을 찍고 재생할 수 있는가?
2. 4마디 구조가 창작을 돕는가, 오히려 제한하는가?
3. 그리드와 오선보를 동시에 보여도 혼란스럽지 않은가?
4. 화음 피드백을 학생이 실제로 이해하는가?
5. 계이름/음이름 병기가 도움이 되는가?
6. 태블릿 세로/가로 화면 모두에서 작곡 가능한가?
7. undo가 모든 편집 명령에서 안정적으로 작동하는가?

## 근거

첫 분석 사례인 `major-minor-composer`에서 확인한 장점은 **작곡 규칙을 설명이 아니라 조작으로 번역하고, 자유도를 단계적으로 조절하는 것**이었다. 자체 구현에서는 이 장점을 유지하면서 음악이론 정확성, 실제 오선보 연결, 리듬 표현, 교사 제출 구조를 확장한다.
